# Re-run a step & cascade — build spec

**Status:** draft for build · **Written for:** the Brain team (cascade engine) + the platform dev (UI).

## Why
Today a mistake in an early stage (e.g. a wrong ICP set in the GTM plan) forces the user to restart the
whole workflow. They should be able to **fix one step and re-run it**, and have **everything downstream
re-run automatically** against the corrected output — without redoing everything, and without accidentally
re-sending email or re-placing calls.

## The foundation already exists
Execution tasks (T1–T11) carry an explicit dependency graph: `brain_plan_tasks.depends_on`. The
orchestrator already runs a task once its `depends_on` are `done`. So "re-run X and everything downstream"
is a graph operation over data the system already has.

## Scope — three levels (phase them)
1. **Re-run an execution task + its dependents** (e.g. Data Research → contacts → email → calls). Contained;
   uses the existing graph. **Build first.**
2. **Re-run from the GTM plan** (fix the ICP → regenerate the plan → cascade into execution). Bigger: the
   plan is produced by the platform's Master Agent and execution runs against a plan snapshot.
3. **Re-run the entire plan** — effectively a fresh run (partly exists today via starting execution again).

---

## Level 1 — re-run a task + its dependents (the core engine, Brain side)

### The cascade
Given a target task `X` for a run:
1. **Compute the downstream set** — `X` plus every task that transitively depends on it
   (`depends_on` closure).
2. **Reset each** to not-done: status → `pending`, clear `achieved_number`/`result`/`last_error`,
   and **clear its produced data** (see below) so stale rows don't linger.
3. **Re-run in dependency order** via the normal worker loop (it already respects `depends_on`).

### 🔴 Safety — the non-negotiable part
A naive cascade would re-run the **email** and **call** steps and **blast the audience again**. The cascade
**must stop at the sending/calling gates**:
- Data/research/content tasks re-run **automatically**.
- **Sending (email) and calling (call) steps re-enter their existing approval gates** (`email_approve`,
  `call_start`) — a human re-approves before anything goes out. Never auto-send on cascade.
- **New references on re-run.** Email/call campaigns are keyed by `reference`; a re-run must mint a **new**
  reference, never resend/redial the old campaign.

### Clearing stale produced data (per task output_type)
When a producing task is reset, delete/supersede what it wrote, so dependents rebuild from fresh output:
- `accounts` (QuickICP companies) → the run's `quickicp_revenueos_client_company_data` rows.
- `contacts` (QuickICP people) → `quickicp_revenueos_client_people_data` rows.
- `emails` / `calls` → the campaign is **not** re-sent; only the task state resets, and a new campaign is
  drafted on re-run (DRAFT → re-approval). Feed rows (`brain_feed_*`) from the old campaign stay as history.
- Each delete is scoped to **this run's customer key** only.

### 💸 Cost confirmation
Re-running data tasks spends credits (QuickICP webhooks, LLM). Before triggering, the platform shows
**"N steps will re-run, M of them paid"** and requires confirmation. The Brain records the confirmation,
the same as the existing paid-step gate.

### Trigger mechanism (platform → Brain)
A re-run request the worker picks up — e.g. a row in a small `revenueos_brain_reruns` table (or a typed
entry on `revenueos_brain_requests`): `{ project_id, target_task_id | 'plan', requested_by, confirmed_paid,
status }`. The worker: validates, computes the closure, resets + clears data, then lets the loop re-run.
It must refuse a re-run while the run is mid-step on an affected task.

## Level 2 — re-run from the GTM plan (spans platform + Brain)
The ICP lives in the **plan**; the plan is generated by the **Master Agent** (platform) from the
checklist/inputs; execution runs against a **plan snapshot** (`revenueos_brain_requests.plan`). So:
1. User edits the ICP (the relevant checklist/plan inputs).
2. Platform **regenerates the plan** (Master Agent).
3. The execution run must **adopt the new plan** and cascade — reset the tasks whose work orders changed
   (at least the data tasks and everything downstream), then re-run with the Level-1 engine and gates.

Open design point: how execution re-points from the old plan snapshot to the regenerated one without
orphaning in-flight state. Simplest safe option: regenerating the plan after execution has started creates
a **new run** seeded from the corrected plan, and the old run is closed — i.e. Level 2 reduces to "new run
from the fixed plan" rather than surgically editing a live run.

## Level 3 — re-run the entire plan
A fresh run from the current plan. Largely exists via starting execution again; expose it as an explicit
"Re-run everything" with the same cost confirmation.

---

## UI (platform)
- On each execution tab/step: a **"Re-run from here"** action (owner-only).
- A confirmation dialog: **which steps will re-run**, **how many are paid**, and a clear note that
  **email/calls will pause for your approval** rather than send automatically.
- On the plan/GTM page: **"Edit ICP & re-run"** (Level 2) and **"Re-run entire plan"** (Level 3).
- While a cascade runs, the Diagnostics/Dashboard already show per-task status — reuse that.

## Acceptance criteria
- [ ] Re-running task X resets X + all transitive dependents and re-runs them in order.
- [ ] Email/call steps in the cascade **do not send/dial**; they return to their approval gate.
- [ ] Re-run campaigns use **new references**; the old ones are never resent.
- [ ] Stale produced data for reset tasks is cleared (scoped to the run's customer).
- [ ] The user sees and confirms **"N steps, M paid"** before anything runs.
- [ ] A re-run is refused while an affected task is mid-step.
- [ ] Level 2: editing the ICP and regenerating produces a corrected run that re-runs data → downstream.

## Phasing
1. **Level 1 engine** (Brain) + **"Re-run from here"** UI (platform) + cost confirmation. Stops at gates.
2. **Level 2** (edit ICP → regenerate → corrected run).
3. **Level 3** explicit "Re-run everything".

## Open questions for the owners
- Reset scope: clear a producing task's data rows, or soft-supersede them (keep history)?
- Level 2: re-point a live run to a regenerated plan, or always spawn a new run from the fixed plan?
- Where the re-run trigger lives: a dedicated table vs a typed `revenueos_brain_requests` entry.
